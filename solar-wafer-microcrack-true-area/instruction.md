I am on the line that checks finished solar wafers right after the copper ribbons are soldered. A wafer that has a fine hairline fracture will have a dead zone that does not light up when we drive current through it for an electroluminescence photo. We use a chilled camera to take that picture.

The picture is not truthful though. When we inject current, the charge does not stay exactly where it was injected, it wanders sideways a little before it makes light, and the camera lens itself is a bit soft. The overall effect is that all the missing light is still present in the image but it has been smeared outward into a pale gray border around the real crack. So what on the real wafer is about one point two square millimetres looks on the monitor like two and a half. The customer report needs the real dead size, not the smeared impression.

You will build the tool that extracts the real size.

The tool lives at /app/solve.py. When we test it we run python /app/solve.py with the path to a scan as the only argument and we read the final token printed to stdout as the answer in square millimetres.

To let you develop we provide one example at /app/data/scene.elcr. You can open it. The hidden grading set is made of completely different wafers with different image extents, pixel pitch, fracture geometry, brightness levels, wafer glow, smear width and camera noise. Those files are handed to your program as randomly named temporary files. Do not hard code any numbers or absolute paths that you see in the example. If you embed the example area the hidden checks will fail.

The ELCR file is our own tiny image container, all numbers little endian. The first four bytes are magic ELCR. The next four bytes are a uint32 version number. The next four bytes are a uint32 type tag, two means each pixel is a signed sixteen bit integer, sixteen means each pixel is a thirty two bit float. The next eight bytes are two uint32 values nx and ny that tell how many pixels there are along x and along y. The following eight bytes are two float32 values sx and sy that tell how many millimetres each pixel covers along x and along y. Those scales are anisotropic and change from file to file so you must read them from the header. The next four bytes are a uint32 file offset where the pixel array starts. Starting at that offset there are nx times ny samples in the declared type, ordered with x varying fastest, so the linear position of x y is x plus nx times y. We already flipped the contrast on export so the fracture is bright over a fairly even wafer glow.

Each file contains one main fracture network that is what we grade. In some files there are also one or two extra tiny bright dots far away from anything else that come from dust or a chipped edge. Those far dots are not part of the grade and must be left out of the number you report.

A simple brightness cutoff does not work. If you are generous and count everything a little brighter than the wafer, you pull in the pale border that belongs to the smear and the number comes out roughly twice as large as reality. If you are strict and count only the very brightest core, you lose the thin side branches that never become fully bright because they only partly fill a pixel, and the number comes out roughly half of reality. No single cutoff works for all wafers because the gain, the overall wafer glow, the smear width and the noise level all move from lot to lot. The key is that the smear moves signal but does not create or erase it.

Even with the blur, the total amount of missing glow is still in the image. Recovering true area is possible if you handle the even background, the far away dust, and the decision of where the pale border actually ends. Getting that combination wrong is why most straightforward approaches are far off.

We check at three percent relative error. Simple threshold methods are well outside that.
